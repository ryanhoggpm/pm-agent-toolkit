# Corpus design

How to structure and write the documents an agent is grounded on. Platform-independent; the
size numbers come from whichever profile in `../platforms/` you build under.

## Structure

**One document per topic, not one per product.** A 500-page manual is the wrong unit. Split it
on its own structure into parts that each fit the ceiling.

**Cut at heading boundaries only.** A part that begins halfway through a procedure is worse
than one that is slightly too big. If a section is itself oversize, cut it at the next heading
level down rather than mid-section.

**Repeat the parent heading on every continuation.** When chapter 6 spans three parts, parts
two and three should open "chapter 6, continued". A part that starts on a subsection with
nothing saying where it belongs is hard to place.

**Spend parts to buy headroom.** Packing into the fewest parts that fit yields parts that all
sit just under the limit, so the next release splits the document again. Aim for a comfortable
margin; parts are free.

**Drop what carries nothing as flat text.** Cover pages, tables of contents, lists of figures.
Page-number cross-references ("see page 41") mean nothing once a document is split into parts
that have no pages.

## The part header

A retrieved chunk arrives without its neighbours, so each part has to identify itself. Five
short sentences, under about 800 bytes:

1. Document name, with part N of M and the functional area
2. One standard sentence on what the product is, used verbatim across every part
3. What this part covers
4. What the other parts cover, **by area rather than enumerated**
5. The version line

Enumerating every sibling puts hundreds of bytes of near-duplicate text in every file, which
competes with real content and blurs retrieval. Describe the areas instead.

Prose, not a metadata table. A YAML block inside an uploaded markdown file is content the
agent can read aloud.

## Voice: the rule that matters most

**Write every source document as though a customer will read it verbatim, because the agent
reads it to them verbatim.**

A source document must not:

- name another document as wrong, or reference a discrepancy between sources
- address the reader with an imperative
- append limitations about topics the document is not otherwise covering
- carry talk tracks, objection handling, or deal mechanics
- tell the reader how to interpret a fact

**This is not style advice.** Agent instructions that explicitly forbade all five did not stop
an agent from doing all five, because its source documents demonstrated them. Rewriting the
documents fixed it and the instructions never changed. The incident is in
`field-notes.md`.

**The example in the retrieved text beats the abstract instruction.** Assume anything a source
document models, the agent will do.

Stating a limitation plainly is fine and stays. That the product lacks a certification is the
correct answer to a direct question about it. What fails is the commentary wrapped around it.

**An absence appears once**, in the document that owns the topic. One document should hold the
canonical list of what the product does not do; no other document repeats an item from it.

**Enablement material is the specific trap.** A positioning guide or competitive battlecard
passes every mechanical pattern check and still does not belong, because its whole genre is
instructions to a seller. Keep the facts, drop the plays. If a document's own first line
describes it as guidance rather than documentation, that is your answer.

## Contradictions

Once retrieval works, an agent that finds two sources disagreeing will reconcile them out loud
in front of a customer. Every instance found this way was a real contradiction nobody knew about:
a heading stating one count while the same page stated another, a total that did not equal the
sum of its parts, a superseded number in three places, schema example values reading as fact.

**Fix these at source.** No amount of work on a synthesis layer stops the narration while the
corpus disagrees with itself. Expect to find them late, because they only surface once
everything is reachable.

## Generated versus authored

Anything derived from a source that will be reissued should be **generated by a script that
records its own arguments**. If a document's provenance is a sentence in a manifest rather than
a command, the next release is a reconstruction.

Authored synthesis documents are the exception: they exist precisely to state a considered
answer that no single source states. Keep them few, number them, and give the numbering
meaning if the agent instructions reference the range.

## Instructions versus documents

Behaviour in the instructions, facts in the documents. Routing rules, refusal policy, tone and
depth are never quoted to a customer, so imperatives are correct there.

**Do not put a wrong value in a prohibition.** An instruction naming the superseded figure it
forbids becomes the only remaining source of that figure once the corpus is clean, and the agent
starts pre-emptively explaining why it does not apply. Prohibitions describe the class, not the
literal.

**Name the scope explicitly, including adjacent subjects.** A scope sentence listing only your
own products will cause refusals on competitor questions, even when a competitor reference
document is attached and indexed.

## Negative claims

An agent's most confident answers are often its absences: no certification, no integration, no
support for X. **A stale document degrades an answer. A stale negative claim reverses one.**

Track every stated absence with the condition that would close it, and re-check them on every
release. Anything that has flipped from absent to shipping blocks the release until its
document, its curated answer and its eval question are all updated.

Three states, not two: still true, now false, and partially addressed. The third is not a
hedge. A release that adds half of a capability leaves a claim that is now half wrong, and it
should be reworded rather than deleted.

## Version authority

Keep one file that states what is current, and resolve every version claim in the corpus
against it. Without that, version facts drift independently in each document and nothing can
check them.
